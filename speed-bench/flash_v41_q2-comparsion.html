Prefill is bound by chunk fill, not by SSD streaming

Streaming a 341 GiB model off SSD looks catastrophic for prompt processing — until the prefill chunks are actually full. The same model, same flags, measured at 2048-token versus 8192-token increments, differs by 3–4× on prefill and not at all on generation.

Why the chunk decides it

Decode touches 6 experts. Prefill touches all 384.

V4.1 Flash routes 6 of 384 experts per layer per token. A prefill chunk takes the union over every token in it, so a large chunk effectively touches all 384 per layer — all 15,360 expert tensors, about 142 GiB, against an 81.5 GiB cache.

That sweep is near-fixed per chunk.

Its cost barely depends on how many tokens ride along. Amortized over 2048 tokens it is ruinous; over 8192 it is four times cheaper per token. Throughput therefore scales with chunk fill, not with cache size.

The flag is clamped by context.

--prefill-chunk 8192 at --ctx-max 8192 silently ran at 4096: prefill_cap is bound by the context allocation. The control run proves the flag alone changes nothing without the tokens to fill it.

Big prefills poison the decode cache.

First-token latency after an 8192-token prefill runs 427–905 ms, against 121–148 ms after a 2048-token one. The sweep evicts exactly the hot experts decode wants back. Steady-state generation is unaffected.

Update · 21 September 2026

Rebuilt on a newer engine, and GLM 5.3 for contrast

Rebuilt from upstream at bd5fe69 — 64 commits past the binaries above — and re-ran the identical 8192-increment sweep. kvcache_bytes matched at every frontier, so the runs compare directly.

+6–12%generation — independently confirmed at +5.5%
−7–13%first-token latency
+5–50%prefill — unconfirmed, see below

Decode: the Engram reader was gated too high.

ds4_engram.c only used its concurrent path above 256 rows, but single-token decode asks for 24 rows per table — so it never qualified and paid full random-read latency on every row, in series. The Apple threshold is now 8. The gain grows with context, which fits: longer contexts spend proportionally more time in that per-token path.

Prefill: probably not real.

Engram cannot explain a 50% gain, and attributing it to the Metal tiling commits was only ever a guess from commit titles. The model's author since ran a teacher-forced, alternated, repeated test and measured 561 → 548 t/s — flat to slightly lower. His method controls for everything these two single runs did not, so treat the prefill gain as unconfirmed.

Context allocation is nearly free.

Re-running the same 8K–32K frontiers at --ctx-alloc 262208 instead of 32833 cost only 2.5% of the expert cache (81.51 → 79.51 GiB) and no prefill at all — 401/399/354/340 t/s against 429/381/287/303, all inside run-to-run noise. An earlier projection of ~50 GiB of context buffers at 262K was wrong; the real figure is 8.80 GiB, because the buffer growth seen between 8K and 32K was mostly prefill_cap doubling, not context scaling.

GLM's first token is ~34 ms.

Against V4.1's 376–786 ms. That gap is the disk tier expressed as latency: V4.1 must fetch Engram rows and missing experts before it can emit anything. For interactive work this matters more than throughput.

And GLM's decode is flat.

−1.9% from 8K to 32K, against −7% for the resident V4 Flash baseline over the same range. Its KV snapshots are ~5.5× larger though, so a given --kv-disk-space-mb budget holds far fewer sessions.

What this does and doesn't establish

  • The resident baseline is DeepSeek V4 Flash Q2 (43 layers, 256 experts, 81 GiB, no Engram), not V4.1. Active footprint per token is close — ~1.94 GiB vs ~2.22 GiB — so it is a fair proxy, but it is not the same checkpoint.
  • The 8192-increment run allocated a 32K context, leaving a smaller expert cache (81.5 GiB / 8793 experts) than the 2048-increment run (86.5 GiB / 9332). It won by 3–4× despite that handicap, which strengthens rather than weakens the result.
  • Single runs, not medians. The docs' own methodology asks for alternating repeats before calling anything a speed result.
  • A live ds4-server reported 216–296 t/s prefill on a 10k prompt at prefill_chunk=8192 — independently consistent with the 215–408 t/s measured here.
